# Plan: Replace `step` CLI subprocess calls with `github.com/smallstep/certificates/ca` library

Status: Draft

## Objective

Eliminate all `step`/`step ca` subprocess invocations from `step-ui-go/` — the Go HTTP handlers (funneled through `runStep()` in `handlers/stepcli.go`, except the two admin-console entries that exec `step` directly via `runAdminConsoleCommand`, `admin_console.go:231` — see R6), and the `entrypoint.sh` shell bootstrap (root-cert fetch, leaf-cert issuance, renew daemon) — by calling `github.com/smallstep/certificates/ca` (pinned `v0.30.2`, same version as the `smallstep/step-ca:0.30.2` image in `docker-compose.yml:27,96`) directly from Go. Remove the `step` CLI binary install from `step-ui-go/Dockerfile`. Net effect: fewer subprocess/exec surfaces (gosec G204 exceptions shrink), provisioner secrets never touch a process argv/`/proc/<pid>/cmdline`, and the image drops one third-party binary + its `sha256sum` pin to maintain.

**The project has no live deployments, operators, or existing volumes yet.** There is nothing to stay backward-compatible with. Breaking changes to config shape, file layout, admin-console command IDs, or startup behavior are all acceptable if they make the result better — this plan does not carry migration/compat baggage, staged-rollout caution, or per-phase safety nets for the sake of protecting an in-production system that does not exist.

Scope explicitly covers two call groups that both currently shell out to `step`:
1. **In-process Go handlers** (`handlers/cert_ops.go`, `certs.go`, `health.go`, `provisioners.go`, `admin_console.go`) — replaced by a new `step-ui-go/stepca` package wrapping `ca.Client`.
2. **Container startup bootstrap** — root-cert-by-fingerprint fetch, leaf-certificate issuance, and certificate renewal (currently `entrypoint.sh:103-233`, shelling out to `step ca root`/`step ca certificate`/`step ca renew --daemon`) move directly into `step-ui-go/main.go`'s own startup path, reusing the same `stepca` package built for group 1 (decision: **Option B**, see Reasoning Transparency — no separate CLI subcommand is built). `entrypoint.sh` shrinks to database/secret wiring only; group 1 alone would not have unblocked `step`-binary removal (see Risk R1), which is why group 2 is in scope at all.

## Acceptance Criteria

- [ ] No occurrence of the literal string `"step"` as an `exec.CommandContext`/`exec.Command` binary name remains anywhere under `step-ui-go/` (verified by `grep -rn 'exec.Command' step-ui-go/` manual review — `df`/`ps`/`ls`/`openssl`/`pg_isready`/`pg_dump` invocations in `admin_console.go` and `backup.go`, plus the `df` disk check in `health.go:483` (`runCheck`), are expected and unaffected).
- [ ] `step-ui-go/handlers/stepcli.go`'s `stepRunner`, `execRunner`, `runStep`, `redactArgs`, `defaultStepTimeout` are deleted; `validIdentifier`/`validateIdentifier` are preserved (relocated per Phase 1) and still enforced before every CSR-bound domain reaches the library.
- [ ] `step-ui-go/Dockerfile` no longer downloads/installs `/usr/local/bin/step` (current install chain: the `wget`→`sha256sum`→`tar`→`mv`→`rm`→`chmod` steps at `Dockerfile:27-33`, chained inside the `RUN` that starts with the `apk add` line at `Dockerfile:26` — the `apk add` line itself stays, see Phase 5.6).
- [ ] `step-ui-go/entrypoint.sh` contains zero `step ` invocations and zero TLS-acquisition logic; it only wires up `DATABASE_URL`/secrets and waits for PostgreSQL. Root-cert fetch, leaf-cert issuance, retry-then-fallback-to-self-signed, and renewal all happen inside `main.go` before/after the HTTP listener starts, per Phase 5.
- [ ] `go.mod` pins `github.com/smallstep/certificates v0.30.2` exactly (no `latest`, no `>=`); `go.sum` committed.
- [ ] `go build ./...`, `go vet ./...`, and `golangci-lint run` (existing config, `.golangci.yml`) pass with zero new suppressions beyond ones explicitly justified in this plan.
- [ ] `go test ./...` passes; `step-ui-go/scripts/coverage-gate.sh` still passes at its current threshold (15%, `step-ui-go/scripts/coverage-gate.sh:25`).
- [ ] Functional correctness, verified against a live `docker-compose up` stack (manual QA, not just unit tests):
  - [ ] `/health`, `/ready` report CA status correctly when step-ca is up and when it is stopped.
  - [ ] `/issue` issues a certificate for each of the 4 templates (`server`, `internal`, `wildcard`, `client`) × representative key types (`EC:P-256`, `EC:P-384`, `RSA:2048`, `RSA:4096`); each resulting cert/key pair is loadable via `openssl x509 -in certificate.crt -noout -text` and `openssl rsa|ec -in private.key -check` (or Go `tls.LoadX509KeyPair`), matches the requested domain/duration/key type.

- [ ] `README.md` bootstrap/TLS-mode documentation (`README.md:243,254,267,274,282,422,452`) updated to reflect the new mechanism.

## Out of Scope

- React/frontend migration — unrelated, no UI framework change here.
- Rewriting the OS-diagnostic admin-console commands (`df`, `ps`, `ls`, `id`, `hostname`, `date`, `openssl version`, `pg_isready`) in native Go — their allowlist definitions (`admin_console.go:84-151`) and the `exec.CommandContext` execution path (`runAdminConsoleCommand`, `admin_console.go:225-276`, exec at `:231`) stay; only the two `step`-backed entries (`step.version`, `step.ca.health`) change. This is also why `openssl` is not dropped from the Dockerfile even though Phase 5 moves self-signed cert generation to Go — see Phase 5.6.
- `pg_dump`/`pg_isready` subprocess calls in `backup.go`/`admin_console.go` — unrelated to `step`, untouched.
- `scripts/step-ca-bootstrap.sh` — this runs *inside the step-ca container*, not step-ui; it uses `jq`, not `step`. No changes needed, confirmed by inspection.
- `AdminClient`/config-management features of the smallstep library (creating/editing provisioners, ACME accounts, etc.) — only `Health`, `Provisioners` (read), `Sign` (issue), `Revoke` are in scope. Anything requiring `ca.NewAdminClient` (mTLS with an x5c admin cert) is a follow-up.
- Let's Encrypt (`le/`, `handlers/le_renewer.go`) — uses `lego`, not `step`, untouched. (Its `StartRenewer()`/background-goroutine pattern is *reused* as a model for Phase 5's UI-cert renewer, but the LE code itself is not modified.)

## Risks

| Risk | Mitigation |
|---|---|
| R1: Root-cert fetch, leaf issuance, and renewal currently run entirely in `entrypoint.sh` (`entrypoint.sh:103-233`) via three separate `step` invocations, outside the Go process altogether. A handlers-only swap of `runStep()` call sites (Phases 1-4) does not touch this shell code at all, so the `step` binary could not actually be removed from the image without also addressing it. | Phase 5 moves all three flows into `main.go`'s own startup path — root fetch, leaf issuance with retry-then-self-signed-fallback, and a background renewal goroutine — reusing the `stepca` package built in Phases 1 and 3. `entrypoint.sh` is reduced to DB/secret wiring; the `step` binary is not removed from the Dockerfile until Phase 5 is verified with a fresh-volume `docker-compose up`. |
| R2: `ca.WithRootFile(...)` reads/parses the PEM **eagerly** inside `ca.NewClient` (**verified against v0.30.2 source**: `NewClient` → `getTransport` → `getTransportFromFile`, `os.ReadFile` + `AppendCertsFromPEM`, errors immediately on a missing/bad file), unlike today's `runStep`, where a missing/unreadable root cert only fails the *current* call. If the Handler is wired to build the CA client once at `NewWithFS` time (like `initOIDC`, `handler.go:64-66`) and `log.Fatalf`s on error, a step-ca that hasn't produced its root cert yet at UI-container-boot would crash the whole UI process — a real regression (today `/ready` just reports the CA as unreachable in its status JSON and keeps serving). | Build the client **lazily and cache-with-retry**: `Handler.caClient()` constructs `stepca.New(cfg)` on first use, caches success, but does **not** cache a *construction* failure — the next call retries construction from scratch. Never `log.Fatalf` on CA client construction. This is an explicit Phase 1 acceptance criterion. This is a correctness/fault-tolerance property of the running process, independent of whether any deployment exists yet. |
| R3: `smallstep/certificates` is pre-v1.0, so semver gives no compatibility guarantee on any 0.x bump. (In practice the `ca` surface this plan uses has been stable — `NewClient`/`NewProvisioner`/`Revoke` signatures byte-identical from v0.25.0 through v0.30.2 — so this is a precaution, not an observed pattern.) | Pin the exact tag `v0.30.2` in `go.mod` (`require github.com/smallstep/certificates v0.30.2`), commit `go.sum`, and do not `go get -u` this dependency without re-running the Phase 0 spike. Dependabot (`.github/dependabot.yml`) will still propose updates — treat any PR touching this dependency as requiring the same manual verification as Phase 0, not an auto-merge. |
| R4: `ca.CreateSignRequest(ott)` generates a fixed EC P-256 key/CSR internally, and **v0.30.2 has no exported bring-your-own-key primitive** at this level (both **verified against source**: `ecdsa.GenerateKey(elliptic.P256(), ...)` hardcoded; the key-accepting `createCertificateRequest` is unexported). The UI currently supports `EC:P-256`, `EC:P-384`, `RSA:2048`, `RSA:4096` (`cert_ops.go:72-74,88,104-108`), so relying on `CreateSignRequest` would silently regress to always-EC-256. | Phase 3 implements local key generation (`crypto/ecdsa`/`crypto/rsa`) + CSR construction (`x509.CreateCertificateRequest`) replicating `CreateSignRequest`'s subject/SAN shape, then builds the `api.SignRequest{CsrPEM, OTT}` value directly — this is the primary design, not a fallback (task 3.1). `api.SignRequest` is a plain struct, so direct construction is supported. Phase 0 spike re-confirms against the pinned tag as a sanity check. |
| R5: `smallstep/certificates` is a large module; even importing only the `ca` subpackage pulls a materially bigger transitive dependency graph (crypto, ACME, X.509, possibly gRPC/Prometheus internals depending on what `ca`/`api`/`provisioner` import) than the current 9 direct deps in `go.mod`. Larger attack surface for `gosec`/Trivy image scan (`.github/workflows/security.yml`), longer CI build. | Accept as a known, bounded tradeoff (this is the entire point of the migration — trade a full CLI binary + its own transitive footprint for a Go library). Run `go mod graph` / `go mod why -m github.com/smallstep/certificates` as part of Phase 7 task 7.3 (once the dependency is in `go.mod`, any earlier spot-check is optional) and record the dependency delta in the PR description so it's visible in review, not silently absorbed. |
| R6: `admin_console.go`'s allowlist-execution model (`runAdminConsoleCommand`, `admin_console.go:225-276`) assumes every command is an OS subprocess (`exec.CommandContext(cctx, c.Name, c.Args...)`). The two `step`-backed entries need to become native Go calls without breaking the "single allowlist is the only place commands are defined" invariant stated in the code comment (`admin_console.go:80-82`). | Phase 4 adds a `Native bool` + `NativeFn func(ctx, stepca.CA) (string, error)` field to `adminConsoleCommand` rather than special-casing IDs in `AdminConsolePost`. `runAdminConsoleCommand` branches on `c.Native` but keeps the same timeout/truncation/duration/audit-log wrapper for both paths. |
| R7: Revocation (`cert_ops.go:123-136`) currently authenticates via the leaf cert/key being revoked (`--cert`/`--key` flags, no provisioner/password) — i.e. mTLS renewal-style auth, not an OTT. **Verified against v0.30.2 source**: `Client.Revoke(req *api.RevokeRequest, tr http.RoundTripper)` takes the mTLS transport as an `http.RoundTripper`, AND the server's mTLS revoke path additionally requires `req.Serial` to exactly match the presented peer certificate's serial (else `403`) and `req.Passive == true` (non-passive revocation returns NotImplemented). A transport-only implementation with a zero-value `RevokeRequest` fails at runtime. | Phase 3 task 3.3 must parse the leaf cert, set `api.RevokeRequest{Serial: <leaf serial, decimal string>, Passive: true, ReasonCode: ...}`, and build the transport from `tls.LoadX509KeyPair`. Additionally an integration-style test against a real (or `httptest`-mocked) step-ca asserts a revoked cert is actually rejected on subsequent use — not just that `Revoke()` returned `nil` error. |
| R8: Coverage/CI gate regression if test migration (Phase 6) is skipped or partial — `cert_backup_test.go`'s `stepRunner`-based tests (`cert_backup_test.go:15-105`) will fail to compile the moment `stepRunner`/`runStep` are deleted, breaking the entire `handlers` package's test suite (not just those 3 tests), which would silently zero out coverage for the whole package. | Phases 1-4 and 6 land together as a single atomic Change Set A (see Steps) — never a commit where the `handlers` package fails to compile. This is a build-correctness requirement, not a rollout-safety one. |
| R9: The provisioner password moves from an out-of-process secret (a file path passed as `--provisioner-password-file` argv, read only by the short-lived `step` subprocess and redacted from logs by `stepcli.go`) to bytes held in the long-lived UI process's own memory for `ca.NewProvisioner`. This widens exposure: heap dumps, `debug.Stack()`-style panics, or accidental struct logging could leak it, and today's argv-redaction guard no longer applies. | Phase 3 task 3.1: read the password file per-issuance and pass it to `ca.NewProvisioner(name, kid, caURL string, password []byte, opts...)` — the password parameter is `[]byte` (**verified against v0.30.2 source**, `ca/provisioner.go:37`), so zero the slice after `Token()` returns. Keep the password a local variable inside the issuance call path only; never store it on the `Handler` or `stepca` client struct, never log the `Provisioner` value. Acceptance criterion: no struct field holds the password beyond the issuance call, and no `slog` call receives the provisioner object. This applies equally to Phase 5's `main.go` bootstrap path, which mints the UI's own leaf cert using the same `Provisioner`/`PasswordFile` config values. |

## Reasoning Transparency

**`entrypoint.sh` bootstrap architecture (R1) — decided.** The project has no live deployment, so the earlier "smaller diff now vs. cleaner architecture later" tradeoff carried no live-user cost either way; the thinker's analysis and the user's sign-off settled on doing it properly the first time.

- **Option B (chosen): move bootstrap into `main.go` itself.** Root-fetch-by-fingerprint, leaf issuance, and renewal move into `main.go`'s own startup path, reusing `handlers.SafeGoExported`/the `StartRenewer()` pattern already established for Let's Encrypt (`handlers/le_renewer.go:18-28`) as the model for a background renewal goroutine, and reusing `tlsreload.go`'s existing mtime-based `certReloader` (`tlsreload.go:38-78`, wired in at `main.go:349-353`) unchanged — the renewer keeps rewriting `cfg.SSLCert`/`cfg.SSLKey` on disk, exactly the same file-write contract as before; there is no switch to an in-memory `ca.NewTLSRenewer`-style config, because `certReloader` already solves "pick up a renewed cert with zero downtime" and duplicating that in-memory would be pure churn. Self-signed generation moves from a shelled `openssl req` (`entrypoint.sh:166-177`) to `crypto/x509` in Go. Result: one TLS code path, in one language, in one process, for all `UI_TLS_MODE` values — `entrypoint.sh` shrinks to DB/secret wiring only, with zero `step` invocations and zero TLS logic.
- **Option A (superseded, not built): a `step-ui ca-bootstrap <root|cert|renew-daemon>` subcommand invoked from an otherwise-unchanged `entrypoint.sh`.** This was the original draft of this plan and remains a valid, fully-specified design (a subcommand dispatch in `main()`, three `flag.FlagSet`-based actions, reusing the same `stepca` package) — kept only as a **one-line escape hatch**: if Phase 0's re-confirmation contradicts the verified `Client.Root` finding, or the in-process renewal flow proves impractical (e.g. a library constraint that only makes sense as a one-shot CLI invocation), fall back to Option A as a stopgap rather than blocking the whole migration on it. Not detailed further here — small enough to reconstruct from the `stepca` package alone (`FetchRootByFingerprint` + `IssueCertificate` are the same two calls either way) if that escape hatch is ever needed.

**Alternatives considered for CA client lifecycle (R2):** eager construction at `NewWithFS` time (mirrors `initOIDC`, `handler.go:64-66`) was rejected because `initOIDC` intentionally `log.Fatalf`s on failure — appropriate for OIDC (an explicit, admin-enabled feature) but wrong for the CA client, which must degrade gracefully (this is precisely why `/ready` and `preflight()` treat CA unreachability as a *reported status*, not a fatal boot error, today). Lazy-construct-with-retry was chosen to preserve that existing fault-tolerance property exactly — this is a runtime-correctness decision, not a migration-safety one.

**Alternatives considered for provisioner-list template compatibility:** rejected changing `templates/provisioners.html` to consume typed provisioner structs directly, in favor of keeping the existing `[]map[string]interface{}{"name":..., "type":...}` contract (`provisioners.go:10,13`, consumed by `provisioners.html:82-83` via `index . "name"`) — smaller diff, and the template has no other dependents that would benefit from typed access.

**What would have to be true for this plan to fail silently:**
- That the locally-built CSR (Phase 3.1's `x509.CreateCertificateRequest` path) produces a *different* SAN/CN shape than `step ca certificate <domain>` did (e.g., puts the domain in `Subject.CommonName` but not `DNSNames`, or vice versa) — tests must assert the actual SAN list on the issued cert, not just "issuance succeeded," or this would ship a working-looking but subtly wrong cert.
- That the Phase 0 re-confirmation is skipped under time pressure — the library facts in this plan were verified against the v0.30.2 module source during review, but the re-confirmation against the actually-fetched pinned tag is the cheap insurance against a transcription error having crept into this document; skipping it removes that check for the price of an hour saved.
- That `Revoke()` returning `nil` is trusted as proof of a working revoke without the R7 mitigation (subsequent-use check) — a Go-level "no error" does not prove the CA actually marked the cert revoked if the wrong auth transport was silently accepted by a permissive test double.
- That nobody exercises the `CA_FINGERPRINT`-from-empty-volume and `UI_TLS_MODE=stepca` paths after Phase 5, since neither has existing automated coverage beyond the new unit tests in Phase 5 (they are process-startup behavior, not request-handling behavior) — a regression here only surfaces on a fresh `docker-compose up`, which is exactly the scenario CI doesn't currently exercise, and (with no live deployment yet) is also the *only* way anyone will notice before this ships.

## Steps

This plan is implemented as two atomic change sets, preceded by a spike. There is no requirement to land each phase as a separate PR or to keep intermediate states independently deployable — with no live users, a single large commit sequence per change set is fine.

- **Spike (not a change set):** Phase 0. Investigation only; its output is a package-doc comment that lands as part of Change Set A.
- **Change Set A:** Phases 1, 2, 3, 4, 6, and cleanup tasks 7.1/7.3. Covers the `stepca` package, all in-process handler call sites, the admin console, and the matching test migration. Merged/committed as one unit because Phase 6 must land atomically with Phases 1-4 (R8) — a partial merge here leaves `handlers` non-compiling.
- **Change Set B:** Phase 5 and cleanup tasks 7.2/7.4. Moves root-fetch/leaf-issuance/renewal into `main.go`, adds the matching `config.Config` fields, and shrinks `entrypoint.sh` to DB/secret wiring. This is a separate change set only because it has a genuine technical dependency on Change Set A (Phase 5 reuses `stepca.Client.IssueCertificate` from Phase 3 and the `stepca.CA` interface from Phase 1) — not because of any rollout-safety staging. If preferred, Change Sets A and B can be combined into one; splitting them here is offered purely for smaller/more reviewable diffs.

### Phase 0 — API surface lock-in (spike, no product code)
Owner: craftsman. Dependencies: none.

1. **0.1** `go get github.com/smallstep/certificates@v0.30.2` in `step-ui-go/`, run `go doc github.com/smallstep/certificates/ca`, `go doc github.com/smallstep/certificates/ca.Client`, `go doc github.com/smallstep/certificates/api` (or read the vendored source under `$GOPATH/pkg/mod/github.com/smallstep/certificates@v0.30.2/ca` directly) to re-confirm, in writing (recorded in `stepca/doc.go` per 0.2):
   The following facts were already verified against the v0.30.2 module source during plan review; the spike's job is to RE-CONFIRM them against the actually-fetched pinned tag (cheap insurance against a wrong assumption having crept into this document) and record them in `stepca/doc.go`:
   - `ca.NewClient(endpoint string, opts ...ClientOption) (*Client, error)`; `ca.WithRootFile(filename string) ClientOption`; `Client.Health()`/`HealthWithContext(ctx)`; `Client.Provisioners()`/`ProvisionersWithContext(...)`; `Client.Sign(req *api.SignRequest) (*api.SignResponse, error)`.
   - `ca.NewProvisioner(name, kid, caURL string, password []byte, opts ...ClientOption)` — password is a **zeroable `[]byte`** (zero after `Token()`, per R9); `Provisioner.Token(subject string, sans ...string) (string, error)`.
   - `ca.WithRootFile` reads the PEM **eagerly** inside `NewClient` (R2 confirmed).
   - `ca.CreateSignRequest(ott)` hardcodes EC P-256 and no exported bring-your-own-key primitive exists — local keygen + `x509.CreateCertificateRequest` + direct `api.SignRequest{CsrPEM, OTT}` construction is the design (R4).

If re-confirmation against the pinned tag contradicts any of the above, or the in-process renewal flow proves impractical, update the affected task descriptions first (0.2) — and only if the library is genuinely unsuitable for in-process use, invoke the Option A escape hatch (Reasoning Transparency).
2. **0.2** Acceptance: findings recorded as package-level doc comments in the new `step-ui-go/stepca/doc.go` (created in Phase 1) referencing exact type/method names and the `v0.30.2` tag, so future readers don't have to re-derive them. If any assumption in this plan's Phase 3/5 task descriptions turns out wrong, update those task descriptions before starting them — don't silently improvise.
